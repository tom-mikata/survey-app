GitHub Issue「選択肢C: DBスキーマ・コード構造の土台整備」の1番目の項目「マイグレーション履歴の再構築」を進めてください。

## 背景
`supabase/migrations/` には3ファイルしか存在せず、いずれも既存テーブルへのALTER文のみです。`departments` / `qq_conditions` / `survey_responses` の `CREATE TABLE` 文がマイグレーション履歴に無く、Supabaseダッシュボード上で手動作成された可能性が高いです。このままだと新しいSupabaseプロジェクト（新しいテスト環境など）を `supabase db push` だけで完全に再現できません。

## やってほしいこと

1. 本番用Supabaseプロジェクト（`survey-app`）とテスト用（`survey-app-dev`）それぞれから、`supabase db dump --schema public` 等でスキーマ定義を取得し、内容に差分がないか確認する。差分があれば報告してください。
2. 取得したスキーマをもとに、`clients` / `departments` / `qq_conditions` / `survey_responses` の完全な `CREATE TABLE` 文（カラム型・デフォルト値・複合主キー・インデックスを含む）を含む新しいベースラインマイグレーションを作成する。既存の3マイグレーションファイル（`20260424000001〜3`）より前の日付になるよう配置する。
3. 本番・テスト両方の既存Supabaseプロジェクトに対しては、このマイグレーションを実際には再実行せず「適用済み」として履歴に登録する（`supabase migration repair <version> --status applied` 等）。既存データ・既存スキーマを一切変更しないこと。
4. 新規にテスト用のSupabaseプロジェクトを1つ作成し、`supabase link` → `supabase db push` のみでスキーマ（テーブル・複合PK・RLSポリシーまで）が完全に再現できることを確認する。確認後、そのテストプロジェクトは削除してよい。
5. 作業内容と確認結果を `docs/01_現行モック整理.md` の「4.3 マイグレーション履歴」の記述と合わせて更新してください（「基本テーブルのCREATE TABLE文が欠落している」という記述はこの対応で解消されるはずです）。

## 注意
- 本番・テスト環境の既存データやスキーマは変更しないでください（あくまで履歴の補完が目的です）。
- 作業が終わったら、GitHub Issueの該当チェックボックスにチェックを入れてください。
