## 1. システム概要

QQメソッド（Quantity and Quality method、プレゼンティーイズム測定手法の一種）に基づき、従業員の健康アンケートを収集し、部署別・年代別・性別に集計したダッシュボードを表示するWebアプリケーション。`client_code` によるマルチテナント構造を持ち、1つのシステムで複数クライアント企業（現状 `default` と `soxx` の2社）のデータを分離して扱える設計になっている。

主な画面は次の4つ。

| 画面 | パス | 内容 |
|---|---|---|
| アンケート回答 | `/survey` | 従業員が10ステップで健康状態を回答（匿名、ログイン不要） |
| 回答完了 | `/survey/complete` | 送信後の完了画面 |
| 分析ダッシュボード | `/results` | 部署別・全社の損失コスト・痛みの部位ヒートマップなどを可視化（要ログイン） |
| 設定 | `/settings` | 部署一覧・健康問題の選択肢などをクライアントごとに管理（要ログイン） |

## 3. 環境構成とデプロイフロー

### 3.1 環境一覧

| 環境 | ブランチ | URL | Supabaseプロジェクト |
|---|---|---|---|
| 本番 | `main` | https://tom-survey-app.vercel.app | `survey-app`（本番用） |
| テスト | `develop` | https://survey-app-git-develop-tom-5990s-projects.vercel.app | `survey-app-dev`（テスト用） |
| ローカル | - | http://localhost:3000 | テスト用または個人設定 |

本番・テストで **Supabaseプロジェクトが分離**されており、Vercel側もPreview/Productionで異なる環境変数（`NEXT_PUBLIC_SUPABASE_URL` 等）を設定する構成（`SETUP.md` に明記）。

### 3.2 デプロイフロー（`SETUP.md` 記載の想定運用）

```
ローカルで開発
  ↓
develop ブランチにプッシュ → Vercel テスト環境に自動デプロイ
  ↓
テスト環境で動作確認
  ↓
GitHub でPR作成（develop → main）
  ↓
マージ → Vercel 本番環境に自動デプロイ
```

### 3.3 実際のコミット履歴の傾向

`git log` を確認したところ、`main`・`develop` の2ブランチ運用は存在するが、直近の履歴は `develop` への直接コミットが中心で、機能単位の `feature/*` ブランチやPRベースのレビューを経た形跡は見られない（コミットメッセージは日本語でConventional Commits風の接頭辞 `feat:`/`fix:`/`docs:` が使われている）。1人開発だったため妥当な運用だが、4人体制ではレビューフローの整備が必要（別紙「チーム開発プロセス提案」で詳述）。

### 3.4 CI/CD・運用ジョブ

- `.github/workflows/keepalive.yml`: 毎日9:00(JST)に本番・テスト両URLの `/api/keepalive` を叩くGitHub Actions。Supabase無料/低価格プランのプロジェクト自動一時停止を防ぐためのもの。
- `vercel.json`: Vercel Cronで同じ `/api/keepalive` を毎日0:00に実行する設定もあり、**GitHub ActionsとVercel Cronの両方でkeepaliveを行っている**（重複構成。整理の余地あり）。

### 3.5 シークレット管理

APIキー等の秘密情報は **Evernoteで手動管理**（`SETUP.md` に明記）。`.env.local` は `.gitignore` 対象でリポジトリには含まれない。専用のシークレット管理ツール（1Password、Vercel環境変数のみでの一元管理など）は未導入。

Vercelの環境変数（`NEXT_PUBLIC_SUPABASE_URL` 等）は、`main`（Production）と `develop` の固定プレビューURL向けには設定済みだったが、PRごとに新しく発行される使い捨てのプレビューURL（例: `survey-hzie3inh4-...`）には当初設定されておらず、ミドルウェアのクラッシュやログイン処理のフリーズを引き起こしていた。「Preview」環境全体に対して設定するよう修正済み（2026年7月21日）。

### 3.6 ローカル開発環境

これまでSupabase CLIのローカルスタック（`supabase start` / `supabase db reset`）を使った検証は、Docker Desktop未導入のため実施できていなかったが、Docker Desktopを導入し、ローカルでのマイグレーション実行検証が可能になった（2026年7月21日）。今後、新しいSupabaseプロジェクトを作らずにローカルで完結した検証ができる。

## 4. データベース構造

### 4.1 テーブル一覧

| テーブル | 役割 | 主キー |
|---|---|---|
| `clients` | クライアント企業マスタ | `code`（文字列、例: `soxx`） |
| `departments` | 部署マスタ（クライアントごと） | `(id, client_code)` の複合PK |
| `qq_conditions` | 健康問題の選択肢マスタ（クライアントごとにカスタマイズ可） | `(id, client_code)` の複合PK |
| `survey_responses` | アンケート回答本体 | `id` |

`departments` と `qq_conditions` は当初単一PKだったが、マルチテナント対応の過程で複合PKに変更されている（`20260424000003_fix_composite_pk.sql`）。

### 4.2 `survey_responses` の主なカラム

`department` / `age_group` / `gender` / `qq_condition`（健康問題）/ `symptom_days_past30`（過去30日の有症状日数）/ `work_quantity`・`work_quality`（0〜10）/ `had_absenteeism`（欠勤有無）/ `monthly_salary_man_yen`（損失額計算用の月給）/ `we_vigor`・`we_dedication`・`we_absorption`（ワークエンゲージメント3項目）。

### 4.3 マイグレーション履歴

`supabase/migrations/` には4ファイル存在する。

| ファイル | 内容 |
|---|---|
| `20260421000000_create_base_tables.sql` | ベースライン: 4テーブルの初期 `CREATE TABLE` 文 + `qq_conditions` の初期17件シード（`client_code` カラム・RLS・複合PKは後続マイグレーションで追加） |
| `20260424000001_add_clients_and_rls.sql` | `clients` テーブル新設（IF NOT EXISTS）、既存3テーブルへの `client_code` 追加、RLS有効化とポリシー設定 |
| `20260424000002_seed_soxx_demo.sql` | デモ用クライアント `soxx` の部署・回答30件シードデータ（※ `qq_conditions` コピーはPK制約の都合でスキップ） |
| `20260424000003_fix_composite_pk.sql` | `departments` / `qq_conditions` の複合主キー化 |
| `20260424000004_seed_soxx_qq_conditions.sql` | `soxx` の `qq_conditions` を `default` からコピー（000003でPKが複合化された後に実行するために分離） |

**マイグレーション連鎖の設計と検証済み動作**:

ベースライン（000000）→ client_code + RLS追加（000001）→ soxxシード（000002・000004）→ 複合PK化（000003）の順で、`supabase db push` のみで新規環境を完全再現できる。ローカルのSupabase CLIスタック（`supabase start` → `supabase db reset`）で実行検証済み：

| 検証項目 | 結果 |
|---|---|
| 4テーブルすべてが作成されること | ✓ |
| `departments` / `qq_conditions` が `(id, client_code)` の複合PKになること | ✓ |
| 全テーブルでRLSが有効・10ポリシーがすべて作成されること | ✓ |
| シードデータ件数（clients:2, departments:5, qq_conditions:34, survey_responses:30） | ✓ |

本番・テスト両環境のマイグレーション履歴（`supabase_migrations.schema_migrations`）に全5ファイルを登録済み（000000〜000003は `migration repair`、000004は `db push`）。

**テーブルの主キー**: `departments` と `qq_conditions` は当初単一PKだったが、マルチテナント対応の過程で複合PKに変更されている（`20260424000003_fix_composite_pk.sql`）。`clients` の主キーは `code`、`survey_responses` の主キーは `id`（変更なし）。

### 4.4 認証・権限（RLS）設計

Supabase Authの `app_metadata` に `role`（`system_admin` / `client_admin`）と `client_code` を保持し、PostgreSQLのRow Level Securityでテーブルアクセスを制御するマルチテナント設計。

| ロール | 権限概要 |
|---|---|
| `system_admin` | 全クライアントの全テーブルに対しCRUDフル権限 |
| `client_admin` | 自社（`client_code` が一致するデータ）のSELECTのみ |
| `anon`（未ログイン） | `departments`/`qq_conditions` のSELECT、`survey_responses` へのINSERTのみ（アンケート回答用） |

`src/middleware.ts` で `/settings/*` と `/results/*` へのアクセスをログイン必須にしている（未ログイン時は `/login` にリダイレクト）。

### 5.1 特徴・設計上のポイント

- **データアクセス層が分離されている**: `src/lib/storage.ts` にSupabase呼び出しが集約されており、UIコンポーネントが直接Supabase SDKを叩く箇所は限定的。DB構造を変更する際の影響範囲を把握しやすい。
- **ビジネスロジックが独立**: QQメソッドの計算式（`qq-method.ts`）が集計処理（`analytics.ts`）から分離されており、単体テストを追加しやすい構造。
- **`ResultsDashboard.tsx` は1,199行の単一コンポーネントだったが分割済み（マージ待ち）**: グラフ種別・フィルタ・集計呼び出し単位で7ファイルに分割し、状態管理・データ取得を担う本体は433行になった。ロジック変更はなく、純粋なファイル分割。複数人が同時にダッシュボードへ手を入れてもコンフリクトしにくくなる想定。
- **テストコードなし**: unit test・e2eテストの仕組みは未導入（`package.json` にテスト関連の依存・スクリプトなし）。
- **`scripts/seed.ts`**: ローカル/CI用のシードスクリプトが用意されている。

## 6. 現行モックの要件充足状況（提案書9ページとの照合）

提案書9ページの「要件詳細」と現行実装を突き合わせると、以下の差分がある（詳細な評価・提案は別紙「今後の開発環境の提案」参照）。
