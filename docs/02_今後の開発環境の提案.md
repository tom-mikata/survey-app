# 今後の開発環境の提案

作成日: 2026年7月20日
関連資料: 「現行モック整理ドキュメント」

## 決定事項（2026年7月20日）

**選択肢C（現行リポジトリを維持しつつ、対象を絞った土台整備を先行させる）を採用。**

Week1〜2の期間内に、5章「選択肢の比較」で挙げた以下5項目に着手する。

1. マイグレーション履歴の再構築
2. 「実施回」エンティティの追加
3. 回答者識別方式の変更
4. `ResultsDashboard.tsx` の分割
5. 最低限のテスト基盤導入

## 1. 論点

正式受注にあたり、提案時に見せたモック（`survey-app` リポジトリ）をベースに要件（提案書9ページ）を追加実装していくべきか、それとも一旦環境を整理し新規プロジェクトとして立ち上げ直すべきか。

## 2. 判断材料となる技術的な事実

「現行モック整理ドキュメント」の調査結果のうち、この判断に直結するものを整理する。

**現行モックの資産（継続を後押しする要素）**

- 実際に動くプロトタイプとしてクライアントに提示済みで、デザイン（人体図ヒートマップ、配色等）を評価されている。提案書自体が「これをベースに要件を加えていく」という前提で書かれている。
- QQメソッドの損失コスト計算ロジック、部署別/年代別集計、マルチテナント基盤（`client_code` + RLS）はすでに実装・検証済み。
- データアクセス層（`storage.ts`）とビジネスロジック（`qq-method.ts`, `analytics.ts`）がある程度分離されており、DBスキーマ変更の影響範囲は限定的に見積もれる。

**現行モックのギャップ（作り直しを後押しする要素）**

- DBに「実施回（調査ラウンド）」エンティティが存在しない。要件（9ページ）にある「企業と実施回を別エンティティとして管理し、複数回分の比較を可能にする」ためには、`survey_responses` を含む中核テーブルのスキーマ変更が避けられない。
- 回答者の識別方式が要件と異なる（現行: 匿名・識別子なし／要件: 氏名+生年月日）。個人情報を扱う設計への変更となるため、RLSポリシーや入力フォームにも影響する。
- マイグレーション履歴に基本テーブルの `CREATE TABLE` が欠落しており、現状のSupabaseプロジェクトを厳密に再現できない。新しい環境を作る場合はもちろん、既存環境を正しく運用し続ける上でもリスクになる。
- `ResultsDashboard.tsx`（1,199行）の肥大化、テストコード不在は、4人体制での並行開発を始めると開発速度低下やコンフリクトの原因になりやすい。

## 3. 選択肢の比較

### 選択肢A: 現行モックにそのまま要件を積み増す

| 観点 | 評価 |
|---|---|
| 初速 | ◎ すぐに着手できる |
| クライアントとの合意との整合性 | ◎ 提案時の説明・見せた画面と一致し続ける |
| DB設計変更の必要性 | 変わらない（実施回・識別キーの変更はどのみち必要） |
| 中長期の保守性 | △ 技術的負債（巨大コンポーネント、マイグレーション欠落、テスト不在）をそのまま抱える |
| チーム開発への適合 | △ レビュー前提の設計になっていないため、並行作業でコンフリクトが増えやすい |

### 選択肢B: ゼロから新規プロジェクトを立ち上げる

| 観点 | 評価 |
|---|---|
| 初速 | × デザイン・ロジックの再実装が必要で、Week1〜2のプロトタイプ確認スケジュールに間に合わない可能性が高い |
| クライアントとの合意との整合性 | × 「これをベースに」と説明した画面と別物になり、期待値のズレが生じるリスク |
| DB設計変更の必要性 | 最初からクリーンな設計にできる |
| 中長期の保守性 | ◎ 設計時点で複数人開発・テストを前提にできる |
| コスト | × 初期開発費150万円という見積の範囲内で二重に作る余裕は乏しい |

### 選択肢C（推奨）: 現行リポジトリを土台に、DBスキーマとコード構造だけ計画的にリファクタする

現行のUI・デザイン・計算ロジックという「見せてしまった資産」はそのまま活かし、要件と食い違っている部分（DBスキーマ、識別方式、マイグレーション管理、巨大コンポーネント）だけを、Week1〜2の要件ヒアリング期間中に計画的に作り直す。ゼロからの再構築ではなく、対象を絞った土台整備という位置づけ。

**具体的な作業項目**

1. **マイグレーション履歴の再構築**: 現行DBのスキーマを `supabase db dump` 等で正確に洗い出し、`CREATE TABLE` から始まる完全なマイグレーション履歴を作り直す。これにより新しい環境（テスト用/本番用）を確実に再現できるようにする。
2. **「実施回」エンティティの追加**: `survey_rounds`（仮称）のようなテーブルを新設し、`clients 1 : N survey_rounds 1 : N survey_responses` の構造に変更する。複数回実施の比較機能はこの変更が前提になる。
3. **回答者識別方式の変更**: 氏名＋生年月日をキーとするか、それに準ずる識別方法をクライアントと合意した上でスキーマとRLSポリシーに反映する（個人情報を扱う分、RLS設計・同意文言の見直しも伴う）。
4. **`ResultsDashboard.tsx` の分割**: 機能追加が始まる前に、グラフ種別・フィルタ・集計呼び出し単位でコンポーネントを分割し、複数人が同時に触れる状態にしておく。
5. **最低限のテスト基盤導入**: 少なくとも `qq-method.ts` や `analytics.ts` のような計算ロジックにunit testを追加する（詳細はチーム開発プロセス提案の品質管理項目を参照）。

この5項目は、選択肢Aを選んだ場合でも遅かれ早かれ必要になる作業であり、「土台を先に整えてから機能を積む」か「機能を積みながら後で土台を直す」かの順序の違いに過ぎない。要件定義がこれから固まっていく段階（Week1〜2）で先に着手するほうが手戻りが少ない。

## 4. 推奨

**選択肢C（現行リポジトリを維持しつつ、対象を絞った土台整備を先行させる）を推奨する。**

理由は次の3点。

1. クライアントには「このモックをベースに要件を加える」とすでに説明しており、選択肢B（ゼロから作り直し）は合意形成のやり直しと工数の二重発生を招く。
2. 選択肢A（無計画に積み増す）は、実施回エンティティや識別キーの変更をいずれにせよ避けられない以上、後回しにするほど影響範囲が広がる（すでにアンケート回答・ダッシュボード双方がDBに直結しているため）。
3. 選択肢Cで挙げた5項目は提案書のWeek1〜2「要件ヒアリング・プロトタイプ」の期間内に収まる規模であり、Week3〜5の反復開発フェーズに要件変更の影響を持ち込まずに済む。

## 5. 提案書スケジュールとの整合

| 週 | 提案書上の予定 | 追加すべき作業 |
|---|---|---|
| Week1〜2 | 要件ヒアリング・プロトタイプ | 選択肢Cの5項目（マイグレーション再構築・実施回エンティティ・識別方式・コンポーネント分割・最低限のテスト） |
| Week3〜5 | 反復開発・デザイン確定 | 新スキーマを前提とした機能実装（アンケート設計のカテゴリー管理、必須/任意設定など） |
| Week6〜8 | テスト・リリース準備 | 品質検証・セキュリティチェック（個人情報を扱う設計に変わるため、この段階での確認項目が増える点に留意） |

## 6. 未確定で確認が必要な事項

- 回答者識別に氏名＋生年月日を使う場合の、個人情報保護方針（同意取得文言、保持期間、削除方針）をクライアントとどう合意するか。
- 「実施回」の単位（月次／四半期／年次など）と、過去データ（`soxx` のデモデータ含む）をどう移行するか。
- Evernoteでのシークレット管理を継続するか、チーム開発移行にあわせて見直すか（別紙「チーム開発プロセス提案」で言及）。

これらは技術的な選択というより運用・契約上の判断が必要な項目のため、次回クライアントとのヒアリングで確認することを推奨する。
