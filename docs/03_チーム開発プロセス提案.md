# チーム開発プロセス提案（survey-app プロジェクト）

作成日: 2026年7月20日
配布先: プロジェクトリーダー（藤田）、シニアエンジニア（中間）、学生エンジニア2名（津山高専）

## 1. 前提

- クライアント（株式会社SO.様）はITに疎く、要件を事前に固めきることができない。ウォーターフォール型は不向きで、1〜2週間ごとに動く画面を見せてフィードバックを得るアジャイル的な進め方を採用する（提案書のスケジュールとも整合）。
- チームは4人。フルタイム常駐ではなく、リモート・非同期を前提とした体制。

| 役割 | 担当 | 主な責務 |
|---|---|---|
| プロジェクトリーダー | 藤田（Tom） | 要件整理・クライアント窓口・品質管理・全体統括 |
| シニアエンジニア | 中間（リモートレビュー） | 技術設計・アーキテクチャ判断・コードレビュー |
| 学生エンジニア ×2 | 津山高専 | 実装（機能追加・UI調整） |

## 2. 開発サイクル（1〜2週間スプリント）

```
[スプリント開始] 目標・タスク合意
      ↓
実装（学生エンジニア中心、Claude Codeを活用）
      ↓
セルフレビュー → シニアエンジニアレビュー → develop へマージ
      ↓
テスト環境（develop）で動作確認
      ↓
クライアントへデモ・フィードバック取得
      ↓
[振り返り] 次スプリントのタスクに反映
```

- **スプリント長**: 原則1週間。要件が固まりにくいフェーズ（Week1〜2）は柔軟に調整可。
- **定例**: 週1回、進捗共有＋次スプリントのタスク合意（30分程度、オンライン）。リーダー・シニアエンジニア・学生エンジニア全員参加。
- **クライアントデモ**: 1〜2週間に1回、テスト環境（develop）の画面を見せながらフィードバックを収集し、その場で反映可能なものはVibe Coding的にその場で調整する。

## 3. Git運用ルール

現状は `main` と `develop` の2ブランチのみで、`develop` への直接コミットが中心だった（1人開発だったため）。4人体制では以下に切り替える。

### 3.1 ブランチ戦略

| ブランチ | 役割 |
|---|---|
| `main` | 本番環境。`develop` からのPRのみでマージ |
| `develop` | テスト環境。`feature/*` からのPRのみでマージ |
| `feature/xxx` | 個別のタスク単位の作業ブランチ。担当者ごとに作成 |

- 命名例: `feature/survey-round-entity`, `fix/results-dashboard-filter` など、内容が分かる名前にする。
- **`develop` / `main` への直接pushは禁止**し、必ずPR経由にする（GitHubのブランチ保護ルールで強制することを推奨）。

### 3.2 コミットメッセージ

現行の `feat:` / `fix:` / `docs:` 等のConventional Commits風の接頭辞を踏襲する。日本語の説明文で可。

### 3.3 プルリクエスト・レビュー

- 学生エンジニアが実装 → PR作成 → **シニアエンジニアが必ず1件以上レビュー**してから `develop` にマージ。
- レビュー観点の目安: DBスキーマ変更の妥当性、RLSポリシーへの影響、既存機能への副作用、命名・型の一貫性。
- 学生エンジニア2人がいる場合は、レビュー負荷分散のため簡単な修正（UI微調整等）は学生同士のペアレビューでも可とし、DB・認証まわりの変更は必ずシニアエンジニアを通す。
- リーダー（藤田）は技術レビューの代わりに、**クライアント要件との整合性**（9ページの要件詳細から逸脱していないか）を確認する役割を担う。

## 4. タスク管理

- GitHub Issues（またはGitHub Projects）でタスクを一覧管理する。口頭・チャットのみでのタスク依頼は避け、必ずIssue化してから着手する。
- 1 Issue = 1 PR を基本単位とし、スプリント内で完了できる粒度に分割する。
- 提案書9ページの「要件詳細」（アンケート設計／集計・分析・可視化／データベース・システム設計）をそのままIssueの初期リストの元ネタとして分解する。

## 5. Claude Code / AIエージェント活用ルール

- リポジトリ直下の `CLAUDE.md`（`AGENTS.md` を読み込む構成）に、Next.js 16の破壊的変更への注意など開発規約を集約している。**学生エンジニアも含め全員がこのファイルを最初に読む**ことを徹底する。
- 環境構築・開発プロセスなど「コードを直接書かない相談」はCowork等の場で行い、具体的な実装指示はClaude Codeに渡す、という役割分担を継続する（今回の整理と同じ流れ）。
- AIが生成したコードでも、DBスキーマ変更・認証まわりの変更は必ず人（シニアエンジニア）のレビューを通す。

## 6. 品質管理

- **Lint / 型チェック**: PR作成時に `npm run lint` と `npx tsc --noEmit` をローカルまたはCIで実行する。
- **テスト**: 現状テストコードが存在しないため、まず `qq-method.ts` の損失コスト計算ロジックなど、金額計算に関わる純粋関数から単体テストを追加していく（Vitest等の軽量な導入を推奨）。
- **デプロイ前チェックリスト**（`main` へのマージ前）:
  - テスト環境（develop）でクライアントの主要導線（アンケート回答→ダッシュボード表示）が動作すること
  - RLSポリシー変更がある場合、`system_admin` / `client_admin` / `anon` の3ロールそれぞれで想定通りの挙動になること
  - マイグレーションファイルが `supabase/migrations/` に過不足なく追加されていること

## 7. シークレット・環境変数管理

現状はAPIキー等をEvernoteで手動管理している。チーム人数が増えるため、以下のいずれかへの移行を推奨する。

- Vercelの環境変数機能に一元化し、閲覧権限をプロジェクトメンバーに限定する
- 1Password等の共有シークレット管理ツールを導入する

学生エンジニアの入れ替わり（卒業・異動）が起こりうる体制のため、**個人のメモアプリ（Evernote）への依存を減らし、アクセス権限を一括管理できる仕組みに寄せる**ことを推奨する。

## 8. オンボーディング

新しく参加するメンバー（学生エンジニアの交代等）向けに、`SETUP.md` を常に最新化する。特に以下を明文化する。

- ローカル環境構築手順（`npm install` → `.env.local` 設定 → `npm run dev`）
- Supabase本番/テストプロジェクトへのアクセス権限の付与手順
- レビュー・PRのルール（本ドキュメントの3章を要約して `CONTRIBUTING.md` 等に転記することを推奨）

## 9. ドキュメント運用

- 本ドキュメントおよび「現行モック整理ドキュメント」「今後の開発環境の提案」は `docs/` フォルダにMarkdownで保存し、リポジトリと一緒にバージョン管理する。
- 大きな設計判断（DBスキーマ変更、認証方式の変更等）が発生した際は、`docs/` に決定事項を追記していく（ADR: Architecture Decision Record的な運用）。

### 9.1 GitHub / Googleドライブの使い分け

以前（Bubbleでの開発時）は、開発ルールや作業記録も含めてGoogleドライブの共有ドライブで一元管理していたが、今後は以下のように使い分ける。

| 保管先 | 対象 |
|---|---|
| GitHub（`docs/` フォルダ） | ソースコード、開発ルール、設計判断の記録、Claude Codeへの作業依頼（`docs/handoffs/`）など、コードと密接に関わり変更履歴が意味を持つドキュメント |
| Googleドライブ（既存の共有ドライブ） | クライアント向けの提案書・契約書、議事録、予算管理など、非エンジニアや共同編集が前提の業務文書 |

このルール自体もGitHub側を正本とし、Googleドライブ側には重複保存しない（両方に置くと更新が食い違うリスクがあるため）。Googleドライブには、必要に応じて「開発ルールは GitHub の `docs/` を参照」という案内のみを置く。

`docs/04_個人情報保護方針_たたき台.md` のように、社内検討中はGitHubで管理し、クライアントとの共同編集段階に入ったらGoogleドキュメントに移す、というケースもある。

## 10. まとめ：役割ごとのアクション

| 役割 | 次にやること |
|---|---|
| リーダー（藤田） | Issue化・スプリント計画の運用開始、クライアントとのデモ日程調整、シークレット管理移行先の決定 |
| シニアエンジニア（中間） | ブランチ保護ルールの設定、レビュー観点のすり合わせ、テスト基盤（Vitest等）の選定 |
| 学生エンジニア | `CLAUDE.md`/`SETUP.md` を読んでローカル環境構築、`feature/*` ブランチでの作業開始 |
