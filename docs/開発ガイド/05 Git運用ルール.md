# Git運用ルール

## ブランチ構成

| ブランチ | 役割 | 直接pushして良いか |
|---|---|---|
| `main` | 本番相当。マージすると自動的にVercel本番環境へデプロイされ、**本番Supabase**に接続する | ❌ 禁止。必ずPR経由 |
| `develop` | 開発の統合ブランチ。Vercelテスト環境と**開発用Supabase**に接続する | ❌ 禁止。必ずPR経由 |
| `feature/xxx` | 機能追加・修正用の作業ブランチ | ✅（自分のブランチのみ） |

ブランチ名の例：
- `feature/issue-20-survey-form`
- `feature/issue-23-survey-rounds-admin`

issue番号をブランチ名に含めると、何の作業か一目でわかります。

## 基本的な作業の流れ

1. `develop` から最新を取得してブランチを作成
   ```
   git checkout develop
   git pull
   git checkout -b feature/issue-xx-xxx
   ```
2. 実装・コミット（こまめにコミットしてOK）
3. GitHubにpushしてPull Requestを作成（マージ先は **`develop`**）
4. PRを作成すると**Vercel Preview URL**が自動発行される → 自分でそのURLを開いて動作確認
5. 藤田さんまたは中間さんにレビュー依頼
6. 指摘があれば同じブランチに追加コミット
7. 承認後、`develop` にマージ

`develop` → `main` へのマージは藤田さんが判断して行います。自分でマージしないでください。

## 特に気をつけること

- **`main`へのマージ = 本番デプロイ = 本番Supabase（実データ）への接続** です。
- **作業は必ず `develop` からブランチを切ってください。** `main` から切ると古い状態を起点にしてしまいます。
- 迷った時や大きめの変更をする時は、実装前に藤田さんに一声かけてください。
- コンフリクトが発生したら、自己判断で強制的に解決せず、まず相談してください。

## PRの書き方（最低限）

- タイトル：何をしたか一行で（例：「実施回登録画面の実装」）
- 本文：変更内容の概要と、動作確認した内容を簡単に

厳密なテンプレートは今のところ設けていません。まずはこの流れに慣れることを優先してください。
